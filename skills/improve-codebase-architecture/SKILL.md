# 改善程式碼庫架構

浮現架構上的摩擦，並提出**深化機會（deepening opportunities）**：把淺模組變成深模組的重構。目標是可測試性與讓 AI 容易導覽。

這個指令是以專案的領域模型為依據，並建立在共享的設計詞彙之上：

- 呼叫 Skill 工具載入 "codebase-design" 取得架構詞彙（**模組（module）**、**介面（interface）**、**深度（depth）**、**接縫（seam）**、**轉接器（adapter）**、**槓桿（leverage）**、**局部性（locality）**）及其原則（刪除測試、「介面就是測試表面」、「一個轉接器 = 假想的接縫，兩個才是真實的」）。每一則建議都要精確使用這些術語，不要漂移成「component」、「service」、「API」或「boundary」。
- `GLOSSARY.md` 中的領域語言為好的接縫命名；`docs/adr/` 中的 ADR 記錄了這個指令不該重新爭論的決策。

## 流程

### 1. 探索

**掃描之前先界定範圍：YAGNI。** 深化一個模組的回報，在於讓日後對它的變更更容易，所以對程式碼庫中最近有變動的部分要多加重視。在看之前先決定*要看哪裡*：

- 如果使用者指明了方向（某個模組、某個子系統、某個痛點），就採用它，並跳過下方的推論。
- 否則，往前走過一大段 commit 歷史（`git log --oneline`），找出程式碼庫的熱點，也就是那些一再出現的檔案與區域，讓這些路徑先吸引你的注意。如果變更很分散、沒有明顯熱點，就把網撒寬。

先閱讀專案的領域詞彙表（`GLOSSARY.md`），以及你所觸及區域內的任何 ADR。

然後啟動一個子代理走訪程式碼庫。不要遵循僵化的啟發式；有機地探索，並記下你感受到摩擦的地方：

- 在哪裡，理解一個概念需要在許多小模組之間跳來跳去？
- 在哪裡，模組是**淺**的，介面幾乎和實作一樣複雜？
- 在哪裡，純函式只是為了可測試性而被抽出來，但真正的 bug 藏在它們被呼叫的方式裡（沒有**局部性**）？
- 在哪裡，緊耦合的模組跨越接縫洩漏？
- 程式碼庫中哪些部分沒有測試，或很難透過目前的介面測試？

對任何你懷疑是淺的東西套用**刪除測試**：刪掉它會讓複雜度集中，還是只是搬移？「是，會集中」就是你要的訊號。

### 2. 以 HTML 報告呈現候選項

把一個自足的 HTML 檔案寫到作業系統的暫存目錄，讓倉庫裡不會多出任何東西。從 `$TMPDIR` 解析暫存目錄，退而求其次用 `/tmp`（Windows 上則是 `%TEMP%`），並寫入 `<tmpdir>/architecture-review-<timestamp>.html`，讓每次執行都有新的檔案。替使用者開啟它（Linux 用 `xdg-open <path>`、macOS 用 `open <path>`、Windows 用 `start <path>`），並告訴他們絕對路徑。

報告使用**透過 CDN 載入的 Tailwind** 來排版與設定樣式，並在圖表（圖形／流程／序列）能可靠傳達結構的地方使用**透過 CDN 載入的 Mermaid**。把 Mermaid 與手工打造的 CSS/SVG 視覺化混合使用：當關係是圖形狀（呼叫圖、相依性、序列）時用 Mermaid，想要更具編輯風格的東西（質量圖、剖面圖、塌縮動畫）時就用手工打造的 div／SVG。每個候選項都有**前／後視覺化**。要視覺化。

為每個候選項渲染一張卡片，包含：

- **檔案**：涉及哪些檔案／模組
- **問題**：為什麼目前的架構造成摩擦
- **解決方案**：用白話描述會改變什麼
- **好處**：以局部性與槓桿的角度說明，以及測試會如何改善
- **前／後圖表**：並排、自訂繪製，說明淺的狀況與深化
- **建議強度**：`強烈建議（Strong）`、`值得探索（Worth exploring）`、`推測性（Speculative）` 之一，以徽章呈現

報告以**最優先建議**章節收尾：你會先處理哪個候選項，以及為什麼。

**領域用 GLOSSARY.md 的詞彙，架構用 `/codebase-design` 的詞彙。** 如果 `GLOSSARY.md` 定義了「Order」，就說「Order 接收模組」，而不是「FooBarHandler」，也不是「Order 服務」。

**ADR 衝突**：如果某個候選項與既有的 ADR 相牴觸，只有在摩擦真實到值得重新檢視該 ADR 時，才把它浮現出來。在卡片中清楚標示（例如警告提示框：_「與 ADR-0007 相牴觸，但值得重新開啟，因為……」_）。不要列出 ADR 所禁止的每一個理論上的重構。

完整的 HTML 骨架、圖表模式與樣式指引，請見 [HTML-REPORT.md](HTML-REPORT.md)。

現在**不要**提出介面。檔案寫好後，詢問使用者：「你想探索其中哪一個？」

### 3. 盤問迴圈

一旦使用者選定候選項，就呼叫 Skill 工具載入 "grilling"，與他們一起走過決策樹：限制條件、相依性、深化後模組的形狀、接縫背後放什麼、哪些測試能存活。

隨著決策成形，副作用就地發生；呼叫 Skill 工具載入 "domain-modeling"，隨時讓領域模型保持最新：

- **用一個不在 `GLOSSARY.md` 中的概念來命名深化後的模組？** 把該術語加進 `GLOSSARY.md`。如果檔案不存在就延遲建立。
- **在對話中磨利了一個模糊的術語？** 當場更新 `GLOSSARY.md`。
- **使用者以承重的理由否決了這個候選項？** 提議 ADR，措辭如：_「要我把這個記錄成 ADR，讓未來的架構審查不要再重複建議它嗎？」_ 只有當未來的探索者確實需要這個理由才能避免重複建議同一件事時，才提議；跳過短暫的理由（「現在不值得」）以及不言自明的理由。
- **想為深化後的模組探索替代介面？** 呼叫 Skill 工具載入 "codebase-design"，並使用它的「設計兩次」平行子代理模式。
