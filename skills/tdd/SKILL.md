# 測試驅動開發（TDD）

TDD 就是 red → green 的迴圈。這個 skill 是讓該迴圈產出值得保留的測試的參考：什麼是好測試、測試該放在哪裡、反模式，以及迴圈的規則。每個章節在每個循環都適用：在迴圈之前與期間查閱它們，而不是事後。

探索程式碼庫時，如果有 `GLOSSARY.md` 就讀一讀，讓測試名稱與介面詞彙符合專案的領域語言，並尊重你所觸及區域內的 ADR。

## 什麼是好測試

測試透過公開介面驗證行為，而不是實作細節。程式碼可以全部改掉；測試不該跟著改。好的測試讀起來像規格：「使用者可以用有效的購物車結帳」清楚告訴你存在什麼能力，而且它能撐過重構，因為它不在乎內部結構。

範例請見 [tests.md](tests.md)，mock 指引請見 [mocking.md](mocking.md)。

## 接縫（Seams）：測試放在哪裡

**接縫**是你進行測試的公開邊界：在那個介面上，你不必伸進內部就能觀察到行為。測試位於接縫上，絕不針對內部細節。

**只在事先約定的接縫上測試。** 在寫任何測試之前，先寫下受測的接縫並與使用者確認。不在未經確認的接縫上寫任何測試。你不可能測試所有東西，所以事先約定接縫，才能讓測試的心力落在關鍵路徑與複雜邏輯上，而不是每一個邊界情況。

問：「公開介面是什麼？我們該測試哪些接縫？」

當該介面的形狀本身有疑問時（模組有多深、接縫該放在哪、介面該暴露什麼），呼叫 Skill 工具載入 "codebase-design" 取得詞彙。它是 module、interface、depth、seam、adapter、leverage 和 locality 這些術語的共同來源，而且它是供查閱的參考，不是要進行的工作階段。

## 反模式

- **與實作耦合**：mock 內部協作者、測試私有方法，或透過旁路驗證（直接查資料庫，而不是使用介面）。徵兆：重構時測試壞了，但行為並沒有改變。
- **套套邏輯式（Tautological）**：斷言以和程式碼相同的方式重新計算預期值（`expect(add(a, b)).toBe(a + b)`、手動以同樣方式推導的 snapshot、斷言等於自身的常數），所以它是依構造而通過，永遠不可能與程式碼不一致。預期值必須來自獨立的事實來源：已知正確的字面值、推演過的範例、規格。
- **水平切片**：先寫完所有測試，再寫所有實作。批量測試驗證的是_想像中的_行為：你測試的是事物的_形狀_，而不是面向使用者的行為，測試對真正的變更變得不敏感，而且在理解實作之前，你就已經鎖定了測試結構。改用**垂直切片**：一個測試 → 一個實作 → 重複，每個測試都是一顆**曳光彈（tracer bullet）**，回應上一輪循環教你的東西。

## 迴圈的規則

- **先 red 再 green。** 先寫會失敗的測試，然後只寫剛好足以讓它通過的程式碼。不要預期未來的測試，也不要加入臆測性的功能。
- **確認因正確的原因失敗。** 修復前先執行新測試。若它直接通過，或因無關原因失敗，先修正測試，再動實作。
- **一次一個切片。** 每個循環：一個接縫、一個測試、一個最小實作。
- **重構不屬於這個迴圈。** 它屬於審查階段（見 `code-review` skill），不屬於 red → green 的實作循環。

## 測試不實際時

寧可不寫測試，也不寫壞測試。壞測試指主要在測 mock、綁死實作細節、依賴時序或全域狀態、或需要昂貴基礎設施才能驗證小修改的測試。

遇到這些情況，退回最接近的可執行檢查：重現指令、目標腳本、log 斷言或快照比對。

## 回報證據

最終回報要附上證據，不只是結果：

- 修復前失敗的測試名稱或檢查指令，以及失敗訊息原文。
- 修復後通過的輸出。
- 無法示範修復前失敗時，說明原因與改用的檢查。
