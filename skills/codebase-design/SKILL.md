# 程式碼庫設計

設計**深模組（deep modules）**：在小介面之後藏著大量行為，放在乾淨的接縫上，並能透過該介面測試。凡是在設計或重構程式碼的地方，都使用這套語言與這些原則。目標是為呼叫者帶來槓桿（leverage）、為維護者帶來局部性（locality），並為所有人帶來可測試性。

## 詞彙表

請精確使用這些術語：不要用「component」、「service」、「API」或「boundary」代替。一致的語言就是重點所在。

**模組（Module）**：任何具有介面與實作的東西。刻意不限定規模：函式、類別、套件，或跨層的切片。_避免使用_：unit、component、service。

**介面（Interface）**：呼叫者為了正確使用該模組所必須知道的一切：型別簽章，但也包括不變量、順序限制、錯誤模式、必要的設定，以及效能特性。_避免使用_：API、signature（太窄，只指型別層級的表面）。

**實作（Implementation）**：模組內部的東西，它的程式碼本體。有別於**轉接器（Adapter）**：一個東西可以是實作很大的小型轉接器（Postgres repo），也可以是實作很小的大型轉接器（記憶體內的假物件）。當主題是接縫時用「adapter」；其餘時候用「implementation」。

**深度（Depth）**：介面上的槓桿。呼叫者（或測試）每學一單位介面，所能施展的行為量。當大量行為藏在小介面之後，模組就是**深**的；當介面幾乎和實作一樣複雜，就是**淺**的。

**接縫（Seam）** _（Michael Feathers）_：一個你可以在不編輯該處的情況下改變行為的地方；模組的介面所在的*位置*。接縫該放在哪裡本身就是一個設計決策，與它背後放什麼是分開的。_避免使用_：boundary（與 DDD 的 bounded context 混淆）。

**轉接器（Adapter）**：在接縫上滿足介面的具體事物。描述的是*角色*（它填補哪個插槽），而不是本質（裡面是什麼）。

**槓桿（Leverage）**：呼叫者從深度得到的東西。每學一單位介面，獲得更多能力。一份實作可以在 N 個呼叫點與 M 個測試上回本。

**局部性（Locality）**：維護者從深度得到的東西。變更、bug、知識與驗證都集中在一個地方，而不是散落在各個呼叫者之間。修一次，處處都好。

## 深 vs. 淺

**深模組** = 小介面 + 大量實作：

```
┌─────────────────────┐
│   小介面            │  ← 少量方法、簡單參數
├─────────────────────┤
│                     │
│  深的實作           │  ← 複雜邏輯被隱藏
│                     │
└─────────────────────┘
```

**淺模組** = 大介面 + 很少的實作（避免）：

```
┌─────────────────────────────────┐
│       大介面                    │  ← 許多方法、複雜參數
├─────────────────────────────────┤
│  薄薄的實作                     │  ← 只是穿透轉手
└─────────────────────────────────┘
```

設計介面時，問：

- 我能減少方法的數量嗎？
- 我能簡化參數嗎？
- 我能把更多複雜度藏在內部嗎？

## 原則

- **深度是介面的屬性，不是實作的屬性。** 深模組在內部可以由小而可 mock、可替換的零件組成；它們只是不屬於介面的一部分。模組可以有**內部接縫**（實作私有、供自己的測試使用），也可以有位於介面的**外部接縫**。
- **刪除測試。** 想像把這個模組刪掉。如果複雜度消失了，它就只是個穿透層。如果複雜度重新出現在 N 個呼叫者之間，那它就是物有所值。
- **介面就是測試表面。** 呼叫者和測試跨越的是同一道接縫。如果你想*越過*介面去測試，這個模組大概是錯誤的形狀。
- **一個轉接器代表假想的接縫。兩個轉接器才是真實的。** 除非確實有東西會在它兩側變化，否則不要引入接縫。

## 為可測試性而設計

好的介面讓測試變得自然：

1. **接受相依性，不要自己建立。**

   ```typescript
   // 可測試
   function processOrder(order, paymentGateway) {}

   // 難以測試
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **回傳結果，不要產生副作用。**

   ```typescript
   // 可測試
   function calculateDiscount(cart): Discount {}

   // 難以測試
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小的表面積。** 方法越少 = 需要的測試越少。參數越少 = 測試設置越簡單。

## 關係

- 一個**模組**恰好有一個**介面**（它呈現給呼叫者與測試的表面）。
- **深度**是**模組**的屬性，相對於它的**介面**來衡量。
- **接縫**是**模組**的**介面**所在之處。
- **轉接器**坐落在**接縫**上並滿足**介面**。
- **深度**為呼叫者帶來**槓桿**，為維護者帶來**局部性**。

## 被否決的框架

- **把深度視為實作行數與介面行數之比**（Ousterhout）：獎勵把實作灌水。我們改用「深度即槓桿」。
- **把「介面」當成 TypeScript 的 `interface` 關鍵字或類別的公開方法**：太窄：這裡的介面包含呼叫者必須知道的每一項事實。
- **「Boundary」**：與 DDD 的 bounded context 混淆。請說**接縫**或**介面**。
