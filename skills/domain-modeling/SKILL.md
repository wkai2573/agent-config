# 領域建模

在設計的同時，主動建立並磨利專案的領域模型。這是_主動_的紀律：質疑術語、發明邊界情境案例，並在詞彙與決策成形的當下就把它們寫下來。（僅僅為了詞彙而_閱讀_ `GLOSSARY.md` 不屬於這個 skill：那是任何 skill 都能做的一行習慣。這個 skill 是用在你要改變模型的時候，而不只是使用它。）

## 檔案結構

大多數倉庫只有單一情境（context）：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目錄存在 `GLOSSARY-MAP.md`，代表這個倉庫有多個情境。該地圖會指出每一個放在哪裡：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 全系統層級的決策
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 特定情境的決策
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

延遲建立檔案：只有在你有東西要寫時才建立。如果不存在 `GLOSSARY.md`，就在第一個術語確定時建立一個。如果不存在 `docs/adr/`，就在需要第一份 ADR 時建立。

## 在工作階段期間

### 對照詞彙表提出質疑

當使用者使用的術語與 `GLOSSARY.md` 中既有的語言衝突時，立刻指出來。「你的詞彙表把『取消』定義為 X，但你似乎指的是 Y。是哪一個？」

### 磨利模糊的語言

當使用者使用含糊或被過度使用的術語時，提出一個精確的標準術語。「你說的『帳號』：是指客戶（Customer）還是使用者（User）？這是不同的東西。」

### 討論具體情境

當在討論領域關係時，用具體情境對它們做壓力測試。發明能探測邊界情況的情境，逼使用者對概念之間的界線說得精確。

### 與程式碼交叉比對

當使用者陳述某件事如何運作時，檢查程式碼是否同意。如果發現矛盾，就把它浮現出來：「你的程式碼會取消整張訂單（Order），但你剛才說可以部分取消。哪一個才對？」

### 就地更新 GLOSSARY.md

當一個術語確定時，立刻在當下更新 `GLOSSARY.md`。不要累積起來一起處理：隨著它們發生就記錄下來。使用 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md) 中的格式。

`GLOSSARY.md` 應完全不含實作細節。不要把 `GLOSSARY.md` 當作規格、草稿區或實作決策的存放處。它是詞彙表，僅此而已。

### 謹慎地提議 ADR

只有在以下三項全部成立時，才提議建立 ADR：

1. **難以逆轉**：日後改變心意的成本相當可觀
2. **缺少脈絡就令人意外**：未來的讀者會納悶「他們為什麼這樣做？」
3. **真正取捨的結果**：確實有其他選項，而你出於特定理由選了其中一個

只要缺少三者之一，就略過 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
