# ADR 格式

ADR 放在 `docs/adr/`，使用連續編號：`0001-slug.md`、`0002-slug.md`，依此類推。

延遲建立 `docs/adr/` 目錄：只有在需要第一份 ADR 時才建立。

## 模板

```md
# {決策的簡短標題}

{1–3 句話：背景是什麼、我們決定了什麼、為什麼。}
```

就這樣。一份 ADR 可以只有一段文字。價值在於記錄*有*做出一個決策以及*為什麼*，而不是把各個章節填滿。

## 選用章節

只有在確實增加價值時才加入。大多數 ADR 都不需要。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：決策被重新檢視時很有用
- **Considered Options（考慮過的選項）**：只有當被否決的替代方案值得記住時才寫
- **Consequences（後果）**：只有當需要點出不顯而易見的下游效應時才寫

## 編號

掃描 `docs/adr/` 找出現有最大的編號，加一。

## 何時提議 ADR

以下三項必須全部成立：

1. **難以逆轉**：日後改變心意的成本相當可觀
2. **缺少脈絡就令人意外**：未來的讀者看著程式碼會納悶「他們到底為什麼這樣做？」
3. **真正取捨的結果**：確實有其他選項，而你出於特定理由選了其中一個

如果決策很容易逆轉，就略過：你到時候直接逆轉就好。如果它不令人意外，沒人會納悶為什麼。如果沒有真正的替代方案，除了「我們做了顯而易見的事」之外，沒什麼好記錄的。

### 什麼符合條件

- **架構形狀。**「我們使用 monorepo。」「寫入模型採事件溯源，讀取模型投影到 Postgres。」
- **情境之間的整合模式。**「Ordering 與 Billing 透過領域事件溝通，而不是同步 HTTP。」
- **帶有鎖定效應的技術選擇。** 資料庫、訊息匯流排、驗證提供者、佈署目標。不是每個函式庫：只有那些要花一整季才換得掉的。
- **邊界與範圍的決策。**「客戶資料由 Customer 情境擁有；其他情境只透過 ID 參照它。」明確的「不」和「是」一樣有價值。
- **刻意偏離顯而易見路徑的做法。**「我們使用手寫 SQL 而不是 ORM，因為 X。」任何會讓合理的讀者假設相反的事情。這能防止下一位工程師去「修正」某個刻意為之的東西。
- **程式碼中看不到的限制。**「因為合規要求，我們不能使用 AWS。」「因為合作夥伴 API 的合約，回應時間必須在 200ms 以內。」
- **否決的理由並不顯而易見的替代方案。** 如果你考慮過 GraphQL 並因為微妙的理由選了 REST，就記下來；否則六個月後又有人會提議 GraphQL。
